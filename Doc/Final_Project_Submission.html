1. What Is This Project?

The Problem We Solved

If you have ever stayed in a college hostel, you know the drill. You want to go home for the weekend. You fill a paper form. You submit it to the warden. The warden is busy, or not around. You wait. When you finally get out, the security guard at the gate barely glances at your paper pass. Your parents have no idea when you left or if you came back safely.

This is how most college hostels work today — paper forms, manual registers, zero real-time visibility. If a student does not return on time, the warden finds out only the next morning. There is no alert, no record, no accountability.

Our Answer — IN-OUT

IN-OUT is a complete digital system that replaces every piece of paper in that process. It is a web application — meaning students, wardens, and gate security all use it on their phones or computers, right there on the college Wi-Fi. No extra app to install. No internet needed.

Module What It Does Who Uses It
GATE Security guard scans a student's ID at the gate. Logs entry and exit. Parent gets an SMS. Gate Security Guard
HOSTEL Full leave management — student applies, warden approves, gate verifies, everyone gets notified. Students, Warden, Admin

2. What We Set Out to Do

We had clear goals when we started this project to make it ready for a real-world college:

  • No more paper forms: Students apply from their phone, warden sees it instantly.
  • No more guessing: Warden can see who is inside the hostel at any time.
  • No more late realisation: If a student is overdue, parents and warden get an SMS alert automatically.
  • Works offline: The system runs on a single college PC and works over the campus Wi-Fi. No internet required.
  • Covers every pass type: Same-day outing, multi-day leave, and emergency exits.
  • Full audit trail: Every action is recorded. Nothing can be disputed or faked.
Summary: We wanted to build something that a real college could actually start using today — not just a demo.

3. How the System Works — Step by Step

A Typical Weekend Leave — The Full Story

Step 1 — Student Applies

A student opens the system on their phone (by scanning a QR code printed in the hostel). They log in with their roll number and select "New Request". They choose Leave (or Outing for a same-day trip), fill in where they are going, when they plan to return, and why. If it is a working day, the form asks them to confirm they have obtained a letter from their HOD.

Step 2 — Warden Reviews

The moment the student submits, the warden's dashboard lights up — no refresh needed. The warden can see every detail: the student's name, year, department, reason, and travel dates. The warden can call the parents and log that call in the system. Then the warden clicks Approve or Reject.

Step 3 — Student Gets a Digital Pass

Once approved, the student's phone shows a QR code — their digital gate pass. This QR code is unique, linked to this specific approved request, and cannot be reused or faked. The student also gets an SMS confirming approval.

Step 4 — Gate Verification

At the gate, the security guard types the student's roll number (or scans their ID card barcode). The system confirms the student is authorized, and the guard clicks "Confirm Exit". The parent immediately receives a real SMS: "Your ward Ravi has left the hostel campus at 2:30 PM."

Step 5 — Return & Completion

When the student returns, the guard scans again. The system logs the entry. If the student comes back on time, the request is marked Complete. If they are late, an automatic alert is sent to both the parents and the warden. The warden does not have to remember to check — the system handles it.

6. Why We Made These Choices (Client-Ready Decisions)

Every project reaches a fork in the road. Below are the important decisions we made to take this from a "demo" to a real-world system.

Decision 1 — Local Wi-Fi Server, Not the Internet

Option Pros Cons Chosen?
Local Intranet (Wi-Fi) Free. No internet needed. Data stays on campus. Fast. Only works on campus Wi-Fi range. Yes
Cloud Server (AWS) Accessible from anywhere. Monthly cost. Needs internet. Data leaves campus. No
Note: A college hostel is always on campus. Students, wardens, and guards are always nearby. There is no need to pay for cloud hosting or risk data going outside. The startup script detects the Wi-Fi hotspot IP automatically and prints a QR code — students just scan it.

Decision 2 — Real-Time Updates via WebSockets

Option How It Works Chosen?
Polling (old method) Browser asks server "anything new?" every few seconds. Wasteful. No
Socket.IO Server pushes updates to the browser the instant something changes. Zero wasted requests. Yes

Decision 3 — Shared TypeScript Types

Both the frontend and the backend need to agree on what a "leave request" or a "student" looks like. Instead of writing the same definitions twice, we created a shared package (@hostel/shared). If one side changes, the other side immediately shows an error before the code even runs. This eliminates bugs where the frontend expects one field name and the backend sends another.

7. Database Design

HOSTEL Module — 10 Tables

Each table has one clear job. No overlapping, no confusion.

Table Name Stores Key Point
users Warden, Security, Admin accounts Passwords are hashed — never stored in plain text.
students Student profiles + room + parent contacts Has a unique QR token printed on their ID card.
hostel_rooms Room numbers, floor, block, capacity Students are linked to their room.
leave_requests Every leave or outing application The central table — has 9 possible status states.

approvals Warden approval/rejection records Separate from logs so they can be queried for reports.

parent_verifications Log of calls made to parents Records who called, when, and what the parent said.
notifications Every SMS and message sent Tracks success, failure, and delivery confirmation.

8. Security — Production Grade

Because this system handles real student data and controls physical gate access, security was upgraded from a demo to real-world standards.

What We Protected How We Did It
Passwords Stored as bcrypt hashes — even DB admins cannot read them.
API Access Every endpoint requires a JWT token — no token, no access.
Admin Routes Protected by strict Role Guards. Only JWTs with the 'ADMIN' role can create staff or students.
Role Separation Students can't see warden screens. Guards can't access admin functions. Enforced at the API level.
Request Body All inputs validated with Zod schema before touching the database to prevent crashes.
HTTP Headers Helmet.js adds security headers to prevent common web attacks (XSS, Clickjacking).
Rate Limiting Login limited to 50 attempts per 15 minutes — blocks brute-force password guessing.
WebSocket Auth Socket.IO connections require the same JWT token as the REST API to prevent unauthorized socket sniffing.

Enabling Real SMS (Fast2SMS)

To send real SMS to parents:

  • Create a free account at https://www.fast2sms.com
  • Go to your dashboard and copy your API key
  • Open the file HOSTEL/server/.env and GATE/server/.env
  • Paste your key next to FAST2SMS_API_KEY=
  • Restart the server — SMS is now live.
📝 Note: If you leave FAST2SMS_API_KEY empty, the system still works perfectly. It gracefully falls back to logging the SMS message to the console to prevent application crashes during local development.

10. Real-World Upgrades Applied

To make this project suitable for professional client submission, the following upgrades were fully implemented to move it past the "demo" phase:

  • Real SMS Gateway: Removed fake console.log() placeholders and integrated the live Fast2SMS DLT-compliant API for both Hostel and Gate modules.
  • Admin Security Guard: Locked down the student and staff creation API endpoints so they strictly require a secure JWT token AND an Admin Role check.
  • Dynamic Warden Alerts: Removed hardcoded phone numbers. The system now dynamically fetches the current Warden's phone number from the database settings table when a student is overdue.
  • Graceful Degradation: If the API keys for services (like SMS) are not provided, the application catches the error and logs it gracefully rather than crashing the Express server.
  • Clean Environment Configuration: Separated environment variables clearly via .env files for both modules.
